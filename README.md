# gRPC Cross‑Language Microservice with OpenTelemetry

A prediction service split across two languages, wired together with gRPC and
traced end to end:

- **`/api`** — a Node.js (Fastify, TypeScript) HTTP gateway. Translates REST
  into gRPC: `POST /predict` calls the unary RPC, `GET /stream` bridges the
  server‑streaming RPC to Server‑Sent Events.
- **`/sidecar`** — a Python `grpc.aio` server implementing the service. Runs a
  mock numpy inference (~1–2 s of CPU) and caches results in Redis for 60 s.
- **Tracing** — both services export OTLP/HTTP to Jaeger. A single HTTP request
  produces **one** trace spanning both services, because the W3C `traceparent`
  is propagated over gRPC metadata.

```
                                                    ┌──────────────────┐
  client ──HTTP──▶  api (Node/Fastify)  ──gRPC──▶   sidecar (Python)   │
                          │                         │   numpy model    │
                          │                         └────────┬─────────┘
                          │                                  │
                          │                              Redis (60s TTL)
                          └──────── OTLP/HTTP ──────┬────────┘
                                                    ▼
                                         Jaeger  :16686 / :4318
```

---

## Quick start

```bash
docker compose up -d --build
```

Compose waits for Redis and Jaeger to pass their health checks, then starts the
sidecar, then the gateway. Once everything is up:

```bash
curl localhost:3000/predict -d '{"input":[1,2,3]}'
```

```bash
curl localhost:3000/trace-test
```

```bash
curl -N 'localhost:3000/stream?input=1,2,3&steps=5'
```

The Jaeger UI is at <http://localhost:16686>; the trace id returned by
`/trace-test` is directly queryable there.

## Building

```bash
pnpm install
pnpm build
```

`pnpm build` is the single entrypoint. It:

1. **`proto:node`** — runs `proto-loader-gen-types` to emit TypeScript
   definitions into `shared/node/types/`, and copies the descriptor to
   `shared/node/prediction.proto` (loaded at runtime by `@grpc/proto-loader`).
2. **`proto:python`** — runs `python -m grpc_tools.protoc` to emit
   `prediction_pb2.py`, `prediction_pb2_grpc.py` and `prediction_pb2.pyi` into
   `shared/python/`.
3. **`build:api`** — compiles the gateway with `tsc`.

No system `protoc` is required: `grpcio-tools` bundles one, and if the ambient
Python interpreter lacks it the script provisions a throwaway venv at
`.venv/protoc`. `make build` is an alias; run `make help` for the full list.

The generated Node types are **load‑bearing**, not decoration:
`api/src/grpc-client.ts` is typed against `ProtoGrpcType`, so changing the
`.proto` without updating the gateway fails `pnpm build` at the `tsc` step
rather than at runtime.

> **Note:** the codegen flags in `scripts/gen-node.mjs` (`--keepCase`,
> `--longs=Number`, …) must mirror the `protoLoader.loadSync()` options in
> `api/src/grpc-client.ts`. If they drift, the generated types describe a
> different object shape than the loader actually produces.

## HTTP API

### `POST /predict`

```bash
curl localhost:3000/predict -d '{"input":[1,2,3]}'
```

```json
{
  "output": [-0.747, 0.520, 0.007, 0.202, -0.124, 0.028, 0.046, 0.470],
  "score": 0.188,
  "model": "mock-mlp-v1",
  "cached": false,
  "cache_key": "prediction:v1:240dc47c…",
  "compute_ms": 1141,
  "request_id": "req-5",
  "trace_id": "e2d40446037a2e4e48969552a98f43c4"
}
```

Repeat the same request within 60 s and it comes back with `"cached": true`
and `"compute_ms": 0`.

Body fields: `input` (required, 1–4096 numbers), `model` (optional), and
`request_id` (optional, echoed back). Unknown properties are rejected with a
400 rather than silently dropped.

> `curl -d` sends `application/x-www-form-urlencoded`, not JSON. The gateway
> accepts a JSON body under that content type as well, so the one‑liner above
> works as written; `application/json` is of course also accepted.

### `GET /stream`

```bash
curl -N 'localhost:3000/stream?input=1,2,3&steps=5'
```

Query params: `input` (required, comma‑separated numbers), `steps` (1–100,
default 5), `model`, `request_id`. Emits one SSE `message` event per delta and
a terminal `end` event. Disconnecting cancels the underlying gRPC call, so the
sidecar stops working on an abandoned stream.

### `GET /trace-test`

Verifies the whole tracing pipeline rather than just its configuration: it
opens a span, makes a real gRPC call to the sidecar, force‑flushes the span
processor, then polls the Jaeger query API until the trace comes back
containing spans from **both** services.

Returns 200 with `"verified": true` and `"cross_service": true` on success;
503 (with the exporter/query URLs it actually used) if the trace never
appeared, and 502 if the sidecar call itself failed.

### `GET /healthz`, `GET /readyz`, `GET /`

Liveness, readiness (reports sidecar channel state and Jaeger reachability),
and an endpoint index. Both probes are excluded from tracing.

Every response carries an `x-trace-id` header.

## Tracing

Both services export spans over **OTLP/HTTP** to
`http://jaeger:4318/v1/traces`. The Node gateway's gRPC instrumentation injects
a W3C `traceparent` into call metadata; the sidecar's `grpc.aio` server
interceptor extracts it, so a `POST /predict` produces a single trace like:

```
prediction-api      GET /trace-test                                608.4ms
prediction-api      request handler - fastify -> trace-context     602.8ms
prediction-api      trace-test.verify                               17.1ms
prediction-api      grpc.prediction.v1.PredictionService/Predict     16.7ms
prediction-sidecar    /prediction.v1.PredictionService/Predict        6.8ms
prediction-sidecar    GET                             (Redis cache)   4.8ms
```

### The ESM hook (`api/otel-hook.mjs`)

The gateway is ESM. OpenTelemetry's auto‑instrumentation patches modules by
intercepting `require()`, which covers CommonJS dependencies — Fastify's
internal `require('http')`, for example — but **not** modules this codebase
imports with an ESM `import`, notably `@grpc/grpc-js`.

Without the hook the failure is silent and easy to misread: HTTP spans still
appear, the sidecar still emits its own spans, and Jaeger still shows both
services — but no `traceparent` is ever injected, so the sidecar starts a
*separate* trace and `/trace-test` reports `"cross_service": false`.

The fix is to register OpenTelemetry's ESM loader hook before any application
module resolves:

```jsonc
// api/package.json
"start": "node --import ./otel-hook.mjs --enable-source-maps dist/server.js"
```

If `/trace-test` ever reports `cross_service: false`, check that the process was
started through this hook.

### Batching

Both services use a `BatchSpanProcessor` with a 500 ms delay. `/trace-test`
force‑flushes the gateway's processor before querying, then polls Jaeger —
Jaeger assembles a trace from spans that each service exports independently, so
"the trace exists" and "the trace is complete" are different questions. The
integration tests poll for the specific span they assert on for the same reason.

## Caching

The sidecar keys results on `SHA‑256(model, input)` under
`prediction:v1:<digest>` with a 60 s TTL. Cache behaviour is visible on the
response (`cached`, `cache_key`, `compute_ms`) and as attributes on the span.

The cache is **fail‑open**: if Redis is unreachable, every operation degrades to
a miss and the service keeps serving. A cache is not a dependency worth failing
requests over.

The mock model is deliberately both slow and deterministic — a fixed‑depth
forward pass produces the output, and a separate loop burns whatever remains of
the 1–2 s budget. Timing never feeds into the result, so a cached answer is
always identical to a freshly computed one.

## Testing

docker compose up -d --build   # the suite runs against a live stack
pnpm test
```

19 integration tests covering the REST contract, cache hit/miss behaviour,
gRPC server‑streaming (both directly against the sidecar and through the SSE

Override `API_BASE_URL`, `SIDECAR_GRPC_TARGET` and `JAEGER_QUERY_URL` to point

```

`make verify` starts the stack, waits for health, and runs the suite in one go.

## Docker

Both images are multi‑stage and Alpine‑based, well under the 300 MB budget:

| Image | Size |
| --- | --- |
| `ghcr.io/ark2306/grpc-prediction-api` | **251 MB** |
| `ghcr.io/ark2306/grpc-prediction-sidecar` | **189 MB** |

```bash
make size   # asserts the budget
```

What keeps them small: `pnpm deploy --prod` resolves a standalone production
dependency tree (copying the workspace `node_modules` instead would drag in
~110 MB of dev dependencies via the pnpm store); declaration files, source maps
and package docs are pruned; `grpcio-tools` and `binutils` stay in build stages;
and the Python `.so` files are stripped.

`scripts/check-image-size.sh` reads the size from `docker images` rather than
`docker image inspect --format '{{.Size}}'` — under the containerd image store
the latter reports the *compressed* size, which would let an oversized image
pass.

Compose health‑gates startup: Redis (`redis-cli ping`) and Jaeger (admin
endpoint on `:14269`) must be healthy before the sidecar starts, and the
sidecar's gRPC health service must report `SERVING` before the gateway does.

## CI/CD

`.github/workflows/ci-cd.yml`:

1. **build** — installs protoc, pnpm, Node and Python; validates the `.proto`;
   runs `pnpm build`; verifies the generated stubs import; typechecks; runs the
   Python unit tests.
2. **test** — starts Redis and Jaeger with `docker run`, launches both services
   on the runner, smoke‑tests `/predict` and `/trace-test`, then runs
   `pnpm test`. Service logs are dumped on failure.
3. **images** — builds both images with layer caching, enforces the 300 MB
   budget, and brings the composed stack up to confirm it answers.
4. **publish** — on push to `main` (or a `v*` tag), authenticates to GHCR with
   `$GHCR_TOKEN` and pushes both images tagged `main`/`sha-<short>` (or
   `<version>`/`latest`/`sha-<short>` for tags).

`publish` requires both `test` and `images` to pass, so a broken build can never
be promoted. Set `GHCR_TOKEN` as a repository secret with `write:packages`; the
workflow falls back to the automatic `GITHUB_TOKEN` if it is absent.
